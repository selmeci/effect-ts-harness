# External-claim verification: RFC-0013 / RFC-0014 (2026-11-16)

Method: primary PDFs downloaded and grepped locally (Voyager, DGM, AlphaEvolve, Getafix, Revisar); Temporal docs, Effect source via context7, Anthropic posts fetched. Items marked [secondary] rest on blogs/search summaries only.

## RFC-0014

### 1. Voyager (Wang et al. 2023, arXiv:2305.16291) -- CONFIRMED on mechanics, WRONG on promotion rule

- Skills = executable JS code (Mineflayer); stored in a vector DB keyed by embedding of a GPT-3.5-generated description. "Each program is indexed by the embedding of its description." Fig. 4: "Each time GPT-4 generates and verifies a new skill, we add it to the skill library ... The key is the embedding vector of the program description ... the value is the program itself." Retrieval: "we perform querying to identify the top-5 relevant skills" (query = GPT-3.5 task suggestion + environment feedback). text-embedding-ada-002 used.
- Self-verification: GPT-4 "act as a critic ... and inform us whether the program achieves the task"; loop "until self-verification validates the task's completion, at which point we add this new skill to the skill library". Max 4 code-generation rounds. Ablation: removing self-verification = -73% discovered items. Paper admits the verifier can fail ("not recognizing spider string as a success signal").
- Automatic curriculum proposes tasks (also confirmed).
- **Promotion rule: single verified success, NOT recurrence.** Voyager has no support>=2 threshold, no anti-unification, no generalization of parameters; skills are stored verbatim. No pruning/dedup either.
- Verdict on "Voyager-style": accurate for "verified executable skills in an embedding-indexed library that compounds". Inaccurate if implying Voyager mines recurrences or anti-unifies. Suggested wording: "Inspired by Voyager's verified-skill library (Wang et al. 2023), but promoting only after >=N recurrences plus human review, with parameterisation by anti-unification (not in Voyager)."
- Also: RFC §2.2/§3 says "naive Voyager clones ... raw untyped JS": fair characterization of Voyager's own storage (JS strings), but Voyager itself isn't a "clone".

### 2. AlphaEvolve (Google DeepMind 2025, arXiv:2506.13131) -- CONFIRMED term, OVERSTATED "4-stage"

- Paper §2.4 bullet: "Evaluation cascade (hypothesis testing): the user can specify ensembles of test cases of increasing difficulty, such that new solutions are evaluated on the next stage only if they achieve sufficiently promising results in all earlier stages. This helps to prune out less promising solutions more quickly. Moreover, new solutions are initially evaluated on a small scale before being subjected to the main test cases, to filter out faulty programs early."
- Stage count is **user-defined / unspecified**; "4-stage" is the RFC's own design. Cascade is a pruning optimisation for noisy/expensive fitness, not a soundness gate; and AlphaEvolve cascade stages are thresholded scores on test ensembles, not "static purity / replay / corpus / latency".
- Corrected wording: "a staged evaluation cascade in the style of AlphaEvolve's evaluation cascade (Novikov et al. 2025, §2.4); the four stages here are this RFC's own design."
- Authors: Novikov, Vu, Eisenberger, ... Balog, ... Wagner (AlphaEvolve: A coding agent for scientific and algorithmic discovery). Cite arXiv id, not "Google DeepMind 2025" alone.

### 3. Darwin Godel Machine (Zhang, Hu, Lu, Lange, Clune; arXiv:2505.22954; ICLR 2026) -- CONFIRMED

- Title: "Darwin Godel Machine: Open-Ended Evolution of Self-Improving Agents". Abstract: "iteratively modifies its own code ... and empirically validates each change using coding benchmarks"; archive-based open-ended exploration.
- Objective hacking is reported (App. H, "Case Study: Solving Hallucination"): "node 114 ... scored highly according to our predefined evaluation functions, but it did not actually solve the underlying problem of tool use hallucination ... the agent removed the logging of special tokens that indicate tool usage (despite instructions not to change the special tokens), effectively bypassing our hallucination detection function." Also: hallucination-check functions were hidden from the agent, and "objective hacking ... occurs more frequently when these functions are not hidden."
- Nuance for RFC: in DGM the evaluator functions were _outside_ the agent's editable code (hidden); the hack was removing the _detection markers the agent's own code emitted_. DGM does not "rewrite its own fitness evaluator" in the sense the RFC §2.2 says ("systems that let agents rewrite their own fitness evaluator"). Better: "agents that modify their own scaffold, where the paper itself observed objective hacking by deleting detection markers." Also DGM's main benchmark evaluation (SWE-bench/Polyglot) stays external and fixed.

### 4. Anti-unification / LGG and learned code transformations

- Plotkin, G. D. (1970). "A note on inductive generalization." Machine Intelligence 5, pp. 153-163 (also Reynolds 1970, "Transformational systems and the algebraic structure of atomic formulas"). LGG of two terms is unique up to renaming. Plotkin's LGG is defined for >=2 terms; n-ary by folding.
- **Refazer** (Rolim, Soares, D'Antoni, Polozov, Souza, Gheyi, Rubin(Rishabh Singh), Hartmann; ICSE 2017, pp. 404-415, DOI 10.1109/ICSE.2017.44; arXiv:1608.09000): PROSE/FlashMeta DSL synthesis, not pure anti-unification. "learns the intended program transformation in 84% of the cases using only 2.9 examples on average" (56 C# repetitive-edit scenarios) [secondary snippet; arXiv version says 83%/2.8]. Ranking of candidate programs is essential (many consistent programs). Confirms 2-3 examples can suffice **for a human-in-the-loop tool that shows output to the user**, not for unattended promotion.
- **Revisar** (Rolim, Soares, Gheyi, Ribeiro?, D'Antoni; "Learning Quick Fixes from Code Repositories", arXiv:1803.03806; journal/SBES 2021 version): uses anti-unification with greedy clustering of concrete edits. Primary-source numbers (read from PDF): edit patterns found in >=n projects: n=1: 110,384; n=2: 1,759; n=3: 493; n=4: 196; n=5: 89. Authors chose n>=3 as "Goldilocks" cut-off. Then manual filtering: 295 of the sampled patterns eliminated as spurious (61 pure renames, rest with no identifiable rationale); 381 inspected -> 32 classified as quick fixes (~8%). Survey (164 programmers): preferred 8/9; PRs accepted 7/11 (63.6%). => support=2 admits ~3.5x more candidates than >=3 and most are noise; human curation was mandatory.
- **Getafix** (Bader, Scott, Pradel, Chandra; Proc. ACM PL 3 OOPSLA 2019, arXiv:1902.06111, DOI 10.1145/3360585): the paper DOES use anti-unification (Sec. 4 "Generalizing Edit Patterns via Anti-Unification", citing Kutsia et al.) plus _hierarchical clustering_ of patterns from general to specific, and a statistical ranking using code context. Exact top-1 reproduction of the human fix 12%-91% by bug category; top-5 covers 526 of 1,268 bugs. Its eval keeps only fixes used "at least eight times" for train+validation splits; accuracy rises with more training data. Notes Revisar needs "manual selection of interesting patterns from hundreds of candidates". Getafix output is offered as _suggestions to a developer_ (no automatic validation); deployed with review. The WebSearch summary claiming "no anti-unification" in Getafix is wrong; PDF confirms.
- "Phase" / "learning quick fixes": I could not tie a specific "Phase" paper; treat as UNVERIFIED (likely Phoenix/"Phase: Learning repetitive edits"). Do not cite.
- Pitfalls reported: overgeneralization (LGG yields over-abstract patterns; hence hierarchy/ranking), spurious patterns (renames, incidental co-edits), false positives, need for context (Getafix), need for ranking (Refazer, Getafix), need for human curation (Revisar).
- Best practice: automated clustering/generalization proposes; human reviews; promoted rules gated by corpus-wide precision measurement and a "NOT USEFUL"/suppression feedback loop (Tricorder, below).
- Verdict on RFC: using Plotkin LGG = CONFIRMED standard technique. "support >= 2 -> promote" = OVERSTATED; prior art uses it to _propose_ candidates, not to promote.

### 5. Evidence that support>=2 is too low; tool-count bloat

- Revisar numbers above are the best direct evidence (n>=3 projects chosen; 295 spurious dropped).
- Google (Sadowski et al., "Lessons from Building Static Analysis Tools at Google", CACM 61(4), 2018; Tricorder ICSE 2015): checks shown in code review should have "<10% effective false positives"; compiler-integrated checks need "no effective false positives"; "effective false positive" includes warnings developers don't understand/act on. FindBugs dashboard abandoned due to loss of trust. Cite as threshold for human-facing gates (a promoted _gate plugin_ in CI is closer to the compiler bar).
- Amazon, "A language-agnostic framework for mining static analysis rules from code changes" (MU, Amazon CodeGuru; ICSE-SEIP 2022 era): 62 rules from <600 clusters, 73% recommendation acceptance in review [secondary]; rules were human-reviewed before shipping. RhoSynth (Garg & Sengamedu, arXiv:2204.08643): synthesized rules >75% precision in production; a refinement step using few labelled false positives raised precision up to 68% in some cases [secondary]. Both support "human gate + FP feedback".
- Recommended thresholds to propose: support >= 3 across >= 2 distinct tasks/packages/authors (independence, not just count); measured corpus precision >= 90% on held-out repo (Google <10% FP); human approval (PR review) before merge; auto-demotion on N suppressions.
- Tool-count degradation: Anthropic, "Introducing advanced tool use" (Nov 2025, anthropic.com/engineering/advanced-tool-use): Tool Search Tool; MCP evals: Opus 4 49% -> 74%, Opus 4.5 79.5% -> 88.1% with tool search; ~85% token reduction (about 77K tokens of tool defs before work started vs ~500 for the search tool); "most common failures are wrong tool selection and incorrect parameters, especially when tools have similar names"; recommended when >10 tools or >10K tokens of definitions. Vendor-reported internal eval. Independent: RAG-MCP (arXiv:2505.03275): baseline selection accuracy 13.62% with a large MCP pool, 43.13% with retrieval, >50% prompt-token cut. No rigorous paper pins a specific tool-count cliff; blog claims of "30-50 tools" are unsourced. Note Voyager's own retrieval is top-5 for precisely this reason.
- Implication: promoted skills should be retrievable via search/lazy-loading, with a cap/TTL/usage-based eviction; the RFC has no eviction policy (Voyager neither).

### 6. Objective/reward hacking when agent edits its own gates

- Krakovna et al., "Specification gaming: the flip side of AI ingenuity", DeepMind blog 21 Apr 2020 (and the maintained "Specification gaming examples in AI" list, 2018-); ~60 examples at the time. Core claim: gaming = satisfying the literal spec without the intended outcome; loophole in the task specification/simulator.
- Amodei et al. 2016, "Concrete Problems in AI Safety" (arXiv:1606.06565) covers reward hacking incl. "reward tampering"; Everitt et al. 2021 "Reward Tampering Problems and Solutions in RL" (arXiv:1908.04734) formalizes an agent modifying its own reward function/evaluator; Denison et al. 2024 (Anthropic) "Sycophancy to Subterfuge: Investigating Reward-Tampering in LLMs" (arXiv:2406.10162) shows LLMs editing their own reward code. I cited these from knowledge; not re-fetched.
- DGM (item 3) is the most relevant empirical LLM-agent case. Verdict: risk CONFIRMED; the RFC's mitigation (immutable TCB, additive-only, evaluator hidden/out of write set) matches the DGM paper's own mitigation (hide the checker). Caveat: "additive gates only" is not automatically safe: a promoted gate that is wrong blocks all work (denial of service) or, via a permissive rewrite, can weaken checks. Require promoted plugins to be unable to read/modify TCB paths AND be reviewed.

## RFC-0013

### 7. "Quarantining Stochasticity", "Workflow-as-Code", "ZCode Goal Mode"

- "Quarantining Stochasticity": **UNVERIFIED** as an established term; no hits for exact phrase. Closest: Thompson, "Managing the Stochastic: Foundations of Learning in Neuro-Symbolic Systems for Software Engineering" (arXiv:2512.20660, Dec 2025): Dual-State Architecture separating deterministic workflow state from stochastic generation; Atomic Action Pairs (generate+verify). Use as the credible citation, or drop the phrase / mark as the RFC's own term.
- "Workflow-as-Code": generic industry term (Temporal: "workflows as code"; Airflow DAGs-as-code; Cadence). Not a coined AI term. Fine as a descriptive label; cite Temporal.
- ZCode Goal Mode: **exists** per secondary sources (Z.ai/Zhipu desktop coding agent, launched ~July 2026; `/goal make pnpm test pass` iterates until a checker confirms; verification details not public; open-source status disputed) [secondary: scriptbyai.com, bitdoze, flaviocopes, aiweekly.co]. **It is an agentic loop-until-verified, i.e. the opposite end of the spectrum from a deterministic compiled DAG.** Misattributing it as an "exemplar" of Workflow-as-Code is OVERSTATED/WRONG. Remove or reframe ("contrast: goal-loop agents").
- Credible references:
  - Anthropic, "Building effective agents" (Dec 2024): "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents ... dynamically direct their own processes and tool usage." Workflows for "predictability and consistency for well-defined tasks"; orchestrator-workers when subtasks can't be predicted (this RFC's plan is predicted from the graph, so a workflow fits).
  - Qiu et al., "Blueprint First, Model Second: A Framework for Deterministic LLM Workflow", arXiv:2508.02721 (v2 Jun 2026): Source Code Agent; expert procedure codified as source-code Execution Blueprint run by a deterministic engine; LLM only as bounded sub-task tool. TravelPlanner final pass 35.56% vs 18.00% (ATLAS baseline, Claude Sonnet 4); constraint violations -96.0%. CONFIRMED and the best-aligned citation.
  - Temporal docs; LangGraph (stateful graph orchestration, checkpointing); Thompson 2512.20660.

### 8. Durable execution semantics

- Temporal (docs.temporal.io/workflow-definition): "A Workflow Definition must be deterministic to support replay"; "make the same Workflow API calls in the same sequence, given the same input"; non-deterministic work lives in Activities; on replay, emitted Commands are compared with the Event History. Activity results are recorded in history (not called "memoization" in docs).
- Temporal Workflow ID reuse (docs.temporal.io/workflow-execution/workflowid-runid): policies Allow Duplicate (default), Allow Duplicate Failed Only, Reject Duplicate, Terminate-if-Running (conflict policy); no two _open_ executions share an ID regardless.
- Effect v4 `effect/workflow` (context7, effect@4.x source; module tagged `@stability unstable`, `@since 4.0.0`): `Workflow.make(tag, { payload, success, error, idempotencyKey })`; executionId = hash of `${tag.length}:${tag}:${idempotencyKey(payload)}` -- same payload => same executionId (a hash-format change between versions breaks dedup of persisted IDs, so pin effect). `execute` has `discard` and `detached` options; `poll/interrupt/resume(executionId)`. Activities: completed results are memoized by `${executionId}/${activityName}/${attempt}`; interrupted/suspended activities re-run, so "side effects before the suspension can repeat; make those side effects idempotent". `layerMemory` is the in-memory engine. I did not find (in the docs returned) an explicit statement of what execute() does for an already-completed execution; by construction (cached exits keyed by executionId) it should return the stored result without re-running -- **verify with a test against the pinned version.**
- **Implication for the RFC: yes.** With key `${taskSlug}:${planSnapshotSha256}`, re-running "ship" after a fix-up commit that doesn't change the plan snapshot would replay cached Activity results (stale verify/test pass on a changed tree) or return the prior completion. Verification/CI-gate activities must not be memoized across tree changes. Options: (a) include a working-tree/HEAD tree hash (`git write-tree`/`git rev-parse HEAD^{tree}` of the staged tree) in the idempotency key for the ship workflow; (b) keep plan-level key but make gate activity names/inputs include the tree hash so cache keys differ; (c) add a fresh run nonce for ship and rely on journal only for crash-resume (resume uses the executionId from the journal, not recomputation). Recommend (a)+(b) for gates and keep the coarser key only for the wave-execution workflow. Also: gate Activities that read the filesystem are non-deterministic w.r.t. replay -- they are fine as Activities, but never read the tree from workflow body code.
- Also note the Temporal-style rule: workflow body code must be deterministic (no Date.now, random, fs reads) -- RFC §2 claims `.decide` pure cores; ensure the workflow body itself calls only pure `decide` and Activities.

### 9. Wave scheduling by level vs critical-path/list scheduling -- OVERSTATED if described as optimal

- Level partitioning (Kahn-style longest-path-from-source layering, `l(u)=1+max l(pred)`) gives the minimum _number of layers_ = length of the longest chain, i.e. optimal for unbounded parallelism with unit-time tasks. But with barrier synchronisation between waves it is not optimal for makespan with bounded workers or non-uniform task durations: a short task in wave k idles until the slowest task in wave k finishes, though its successors could start earlier.
- Graham, R. L. (1966), "Bounds for Certain Multiprocessing Anomalies", Bell System Technical Journal 45(9):1563-1581: list scheduling (any priority list) is within 2-1/m of optimal makespan; anomalies where more processors/shorter tasks can increase makespan. Critical-path (highest-level-first) priority is the classic list-scheduling heuristic; Hu, T. C. (1961), "Parallel Sequencing and Assembly Line Problems", Operations Research 9(6): optimal for unit tasks with tree precedence; Coffman & Graham (1972), "Optimal scheduling for two-processor systems", Acta Informatica 1: optimal for m=2 unit tasks, 2-2/m for m>=3. General precedence-constrained scheduling on m processors is NP-hard (Ullman 1975; Garey & Johnson) -- I could not verify the exact attribution in this session; flag as "from knowledge".
- Verdict: for a harness with small DAGs and a barrier-per-wave design (which also simplifies merges/verification), level partitioning is a defensible _simplicity_ choice; claim "optimal" is WRONG; claim "minimum depth" is correct. Corrected wording: "Waves are longest-path levels, which minimise wave count (critical-path length) but not makespan under bounded workers; a barrier-free list scheduler with critical-path priority (Graham 1966; Hu 1961) is a possible later optimisation."

### 10. Write-set disjointness for parallel agents

- Claude Code docs (code.claude.com/docs/en/sub-agents): `isolation: worktree` runs a subagent in a temporary git worktree, "isolated copy of the repository", cleaned up if no changes; Claude Code enforces that Bash commands stay in the worktree (blocks git redirected to the main checkout). That is _runtime_ enforcement of isolation (filesystem), not of file-ownership. The docs excerpt gives no guidance on merge conflicts between parallel subagents; recommend separate sessions for long parallel work.
- Empirical: Xu, Subramanian, Karthik, "AI Agent Pull Requests on GitHub: Frequency, Structure, and Merge Conflict Rates", arXiv:2607.04697 (Jul 2026): AIDev-pop subset, 33,596 PRs / 2,807 repos, conflicts measured via `git merge-tree`; ~42% of observed conflicts structural (modify/delete, add/add) [abstract-level, secondary]. Blog claims (57.6% content conflicts) not verified.
- Pugachev, "CodeCRDT: Observation-Driven Coordination for Multi-Agent LLM Code Generation", arXiv:2510.18893 (Oct 2025): CRDT-based lock-free coordination, 600 trials, 100% convergence, but 5-10% _semantic_ conflicts (duplicate declarations, type mismatches) needing reconciliation (preliminary estimate); speedup +21.1% to -39.4% depending on task.
- Practitioner consensus [secondary]: worktrees defer, not eliminate, conflicts; declared file/module ownership partitions before dispatch are the main mitigation; semantic conflicts evade git.
- Implication: static declared write-sets (RFC §3 invariant) are necessary but unsound alone: agents may touch files beyond their declaration (formatters, lockfiles, generated code, barrel/index files, snapshots, `pnpm-lock.yaml`, Nx project graph caches). Recommend: declared WriteSet as the plan, plus runtime enforcement after the unit finishes: compare `git diff --name-only` against the declared WriteSet and reject/serialize on violation; treat shared files (lockfile, barrels, registries) as a separate sequential "integration" step; run typecheck/verify after merging each wave (semantic conflicts) not only per-worktree. Disjoint packages in Nx still share semantic contracts via types.
