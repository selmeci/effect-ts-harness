## 14. Internal inconsistencies in RFC-0012

1. Commit flag: G1 (L70) and G2 (L71) use `commit: false`/`commit: true` booleans. The schema (L215) is `CodemodCommitMode = "dry-run" | "atomic-commit"`. The port input (L363) has `mode`. ## 15. README row vs body

README L169 names: `harness_codemod_apply`, `CodemodTransaction.decide`, `ShadowOverlayPort`, "SHA-256 OCC", "Immutable TCB protection", "zero-regression LSP & syntax-bans validation". README L227 (mermaid) and L242 repeat `harness_codemod_apply`. Body (RFC-0012) names: `harness_shadow_codemod`, `ShadowCodemodGuard.decidePath`, `CommitGateDecision.decide` (L86 only), `ShadowCodemodPort`. Also README title says "Dry-Run In-Memory `ts-morph` + `@ast-grep/napi` Refactoring with Atomic Rollback" while the RFC title says "Transactional Multi-File AST Codemods in Shadow LSP (harness_shadow_codemod) with All-or-Nothing Commit". RFC-0014 (L312) uses `harness_shadow_codemod`, so the body is the canonical name and README must change. `CodemodTransaction.decide` and `ShadowOverlayPort` do not appear in the body at all (grep: 0 hits).

SHA-256 OCC: the body does NOT implement compare-before-rename. `sha256Before` is stored in `CodemodFileDiffSummary` (L222) and the commit step "Snapshot original file hashes (`sha256Before`) and contents in memory" (L135), but there is no step that re-reads disk and compares with `sha256Before` immediately before rename, and no error type for a stale-base conflict (`CodemodStaleBaseError` or similar is missing from the E union L373-376). There is also a TOCTOU window between the snapshot and the rename, and between the shadow verification (against `W_disk` read at start) and the commit. Concurrent edits by a human or another worktree-sharing subagent would be silently overwritten (rename replaces atomically with no check). Correction: either add a compare-before-rename OCC step plus a `CodemodConcurrentModificationError` and an `expectedSha256` check, or delete "SHA-256 OCC" from the README row.
