## 2. CRITICAL semantics (from source)

(a) Re-execution of a COMPLETED execution: engine returns the stored result; it does NOT re-run.

- Execution id = hash(`${tag.length}:${tag}:${idempotencyKey(payload)}`) - Workflow.ts:340-341.
- layerMemory execute (WorkflowEngine.ts:~790-815): `let state = executions.get(options.executionId); if (!state) { ...create state...; yield* resume(id,"explicit") }` ... `const exit = yield* Fiber.await(state.fiber!)` ... `return (yield* exit)`. Existing state => no new run, caller gets the old fiber's exit (success OR failure). New payload is ignored (first payload wins), so `includeMutateStrict` is not part of identity.
- resume(): `if (exit && exit._tag==="Success" && isUnwakeable(exit.value, mode)) return` (L~741-744) with isUnwakeable = Complete || (automatic && failed) (L~715). A plain workflow failure is a "Complete" result (Workflow.intoResult), so it is never re-run. Only an explicit `resume` on a failure-suspended workflow (annotation Workflow.SuspendOnFailure, L1027, default false) replays.
  (b) Activity memoization: YES, per execution by activity name + attempt. `const activityId = `${instance.executionId}/${activity.name}/${attempt}`; if (state) { ... else if (exit) return yield* exit }` (WorkflowEngine.ts:~917-927; INST :806-815). Cached exit includes FAILURES (the exit is stored on any non-interrupt exit; L~935 "state.exit = Exit.isFailure(exit) && Cause.hasInterruptsOnly(exit.cause) ? undefined : exit"). Attempt number = Activity.CurrentAttempt (default 1; only incremented by Activity.retry, Activity.ts:225-245). Only Suspended results are re-run (Activity.ts:126-129: "Only completed activity results are memoized. If the activity suspends ... its body runs again").
  (c) Durable engine interface: WorkflowEngine Service has 10 methods: register, execute, poll, interrupt, interruptUnsafe, resume, activityExecute, deferredResult, deferredDone, scheduleClock (WorkflowEngine.ts:46-215), plus WorkflowInstance state bookkeeping (L250-300) and the Encoded variant via makeUnsafe. In-tree implementations: only layerMemory (in-memory Maps, WorkflowEngine.ts:726-975) and ClusterWorkflowEngine (src/cluster/ClusterWorkflowEngine.ts:1089 `layer` requires Sharding | MessageStorage). There is NO file-backed engine. The RFC's "lightweight file-backed WorkflowEngine journal" (FileWorkflowEngineLive) is a full custom engine, not an adapter; the <1 ms checkpoint SLO and 650-LOC budget are unsubstantiated. It must also persist suspended state, deferreds, clocks, child parents, and replay compensations.
  (d) Determinism: On wake/resume the engine re-runs the whole workflow body from the top (`state.execute(state.payload, ...)` in resume(), WorkflowEngine.ts:~772-780, "each run gets a fresh scope, so replays rebuild compensations"), with activities served from memo. So everything outside Activity.make must be deterministic and side-effect free (no Date.now/random/FS/CLI reads in the body). Activity.ts:126-129 explicitly warns side effects can repeat. The RFC states none of this; its conditionals (`if (payload.includeMutateStrict)`) are fine, but HarnessTaskWorkflow wave logic must be written accordingly.

Evaluation of idempotencyKey = `${taskSlug}:${planSnapshotSha256}` for AtomicShipWorkflow: BROKEN.

- Ship fails at GcStrict (activity RunGcAndOntologyStrict fails, ShipGateFailedError). Agent fixes code; plan snapshot unchanged => same key => same executionId. `harness workflow ship` -> engine finds existing execution -> returns the CACHED ShipGateFailedError without running anything (workflow ended as Complete(failure)). Even with an explicit resume/SuspendOnFailure, the failed activity's exit is memoized for attempt 1, so GcStrict would return the cached failure.
- Cached successes (RunLearnPreVerifyAndClear, RunFormatCheck) would be replayed although code changed. In a passing path after a success: RunVerifyAndWriteStamp would be served from cache => verify not re-run and verify-stamp.json NOT rewritten; stamp (hash of whole tree) is stale => done fails or seals a stale stamp. This directly defeats G4 and REQ-1.5 (G3) conflicts with G4. A cached "Ship succeeded" also blocks a legit second ship after later edits.
- Fix: key must include a run nonce or the workspace tree hash (computeWorkspaceTreeHash, libs/harness/gates/src/verify-stamp.ts:73) at ship start (or a monotonically increasing attempt counter in the payload), and resumability should apply only to interrupted (suspended) runs, not completed ones. Plan snapshot hash alone is the wrong identity for ship; it can work for the wave workflow only if activity names include the owned-file content hash (RFC Open Question 2 acknowledges this; it should be mandatory, not future work).
- Also: every gate (gc, verify...) is a child-process CLI whose result depends on the filesystem, so Activity memoization is inherently unsound across code edits.
