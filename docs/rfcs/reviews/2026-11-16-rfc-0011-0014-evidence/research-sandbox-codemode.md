# Research: external claims in RFC-0011 / RFC-0012 (sandbox, Code Mode, transactional writes)

Date of research: 2026-11-16. Local experiments ran on Node v24.14.1 (linux), TypeScript 5.9.3. Scripts live in `.../scratchpad/rfc-review/t/`.
Note: WebFetch summaries come from a small model. Quotes marked "verbatim" were returned as verbatim; treat the rest as paraphrase and spot-check before quoting in the RFC.

## Headline findings (act on these)

1. **RFC-0011's core sandbox design is broken as specified.** `codeGeneration: {strings:false}` does NOT stop `fn.constructor(...)` when `fn` is a host-realm function, or when a host-realm value (an array returned by a host bridge, or a thrown host Error) reaches the script. I reproduced a full escape to `process` and `child_process.execSync("id")` on Node 24.14.1 (see B5). The AST blacklist (`.constructor.constructor`, `Proxy`, `Reflect`, ...) is bypassable via string-built keys (`obj['con'+'structor']`), which also defeats the "Phase 1" gate.
2. **`node:vm` is explicitly "not a security mechanism"** (Node 24 docs). The "frozen null-proto context" does not change that.
3. **The Worker adds no capability boundary.** In a Worker, `process`, `require`, `process.getBuiltinModule('fs')` are all present (verified). A vm escape inside the worker yields fs + child_process. Only an OS-level/process-level boundary helps (child process under `--permission`, Deno, workerd, or a separate user/container).
4. **Cloudflare "up to ~99%" is mis-attributed.** 99.9% / 1.17M->~1,000 tokens comes from the Feb 2026 Cloudflare API MCP post (two tools `search`+`execute`), not the Sep 2025 Code Mode post (which has no figure and a single execute tool).
5. **RFC-0012 "atomic rename of N files" is not atomic**, and "O(log k) bisection" is wrong for interdependent edits (ddmin is O(n^2+3n) worst case, and subset bisection is ill-defined when edits depend on each other).

## A. Code Mode claims

### A1. Cloudflare Code Mode / `@cloudflare/codemode` -- PARTLY CONFIRMED, figure OVERSTATED/MIS-ATTRIBUTED

Two distinct Cloudflare posts. The RFC conflates them.

|               | Sep 2025 "Code Mode" post                                                                                                                                        | Feb 2026 "Code Mode MCP" post                                                                                                   |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| URL           | https://blog.cloudflare.com/code-mode/                                                                                                                           | https://blog.cloudflare.com/code-mode-mcp/ (published 2026-02-20 per fetch)                                                     |
| Tools exposed | One tool: "our agent is presented with just one tool, which simply executes some TypeScript code" (no separate `search`)                                         | Two tools: `search()` and `execute()`; footprint "stays fixed, no matter how many API endpoints exist"                          |
| Token figure  | None published. | Sandbox       | V8 isolates on Workers via the Worker Loader API; "The sandbox is totally isolated from the Internet"; access only via bindings; API keys stay in the supervisor | "Dynamic Worker (Dynamic Worker Loader)", "a lightweight V8 sandbox with no file system"; external fetch disabled by default    |

`@cloudflare/codemode` (https://github.com/cloudflare/agents/tree/main/packages/codemode): described as **experimental**; "generates TypeScript type definitions from your tools for LLM context, and executes the generated JavaScript in secure, isolated sandboxes." It exports `createCodeTool`, `generateTypes`, `DynamicWorkerExecutor`, `createCodemodeRuntime` (runtime exposes `search()`, `describe()`, `execute()`), plus `IframeSandboxExecutor` for browsers. `DynamicWorkerExecutor` **requires a Cloudflare Workers environment** (uses `WorkerLoader`, `globalOutbound: null` blocks fetch/connect). So the package is not usable as-is in a local Node MCP server; only the pattern (typed SDK + code) transfers.
Cloudflare's Dynamic Workers docs (https://developers.cloudflare.com/workers/runtime-apis/bindings/worker-loader/ , last updated Oct 31 2026): "the lowest-level primitive for spinning up a Worker."

Corrected wording for RFC-0011 §1/§2.3: "Cloudflare's Code Mode converts tool schemas into a TypeScript API and has the model write code run in a V8-isolate Dynamic Worker (Sep 2025); its Feb 2026 Cloudflare-API MCP server exposes only `search()` and `execute()` and reports a 99.9% input-token reduction (1.17M -> ~1k) on a 2,500-endpoint API. That figure measures schema-size collapse for a huge API, not the harness's N+1 round-trip savings."
Also fix "progressive .d.ts disclosure": the Sep 2025 post says the full generated API is loaded into context and browsing is future work; search-based discovery is the Feb 2026 design.

### A2. Anthropic "Code execution with MCP" and Programmatic Tool Calling -- CONFIRMED figures; neither endorses node:vm

- Code execution with MCP, https://www.anthropic.com/engineering/code-execution-with-mcp, 2025-11-04: token usage drops "from 150,000 tokens to 2,000 tokens" (98.7%). Sandboxing: agent-generated code needs "a secure execution environment with appropriate sandboxing, resource limits, and monitoring"; notes operational overhead. No mention of `node:vm`.
- Programmatic Tool Calling, https://www.anthropic.com/engineering/advanced-tool-use, 2025-11-24: Claude writes **Python** run inside Anthropic's Code Execution tool (a sandboxed environment); you opt tools in with `allowed_callers`; only the final output enters context. Reported figure: "Average usage dropped from 43,588 to 27,297 tokens, a 37% reduction on complex research tasks." This is an API-hosted feature; it is not a recipe for a local Node sandbox.
- Corrected wording: cite 150k->2k (98.7%) and 37% as the two Anthropic numbers; drop any implication that Anthropic endorses `vm`-based sandboxes. Anthropic says "sandboxing, resource limits, monitoring" = OS/container level.

### A3. Evidence that code actions beat JSON tool calls -- CONFIRMED but weaker than implied

CodeAct (Wang et al., ICML 2024), https://arxiv.org/abs/2402.01030: abstract says CodeAct "outperforms widely used alternatives (up to 20% higher success rate)" across 17 LLMs on API-Bank and a new benchmark (M3ToolEval). "Up to"; baseline is text/JSON action formats; I could not confirm a "fewer actions" claim from the abstract (the paper body reports ~30% fewer steps; verify in full text). Cloudflare's "LLMs are better at writing code to call MCP than calling MCP directly" is an assertion without published benchmark. Corrected wording: "CodeAct reports up to 20% higher success than JSON/text actions; evidence is for general tool use, not for graph-join queries, and the harness should benchmark its own eval tool."

## B. Sandbox security and runtime

### B4. `node:vm` "is not a security mechanism" -- CONFIRMED (verbatim)

https://nodejs.org/docs/latest-v24.x/api/vm.html : "The `node:vm` module is not a security mechanism. Do not use it to run untrusted code."
Also documented: `timeout` spawns new event loops/threads (non-zero overhead); `codeGeneration.strings:false` makes `eval`/function constructors throw `EvalError` (this applies to code compiled **in that context**).

### B5. Host-object escape -- CONFIRMED by experiment; the RFC invariant is WRONG

Tests (`t/a.js`, `t/b.js`, `t/c.js`), Node v24.14.1, context created as `vm.createContext(Object.create(null), {codeGeneration:{strings:false,wasm:false}})`:

- Inside the context, `(function(){}).constructor('return 1')()` -> `EvalError` (the option works for in-realm functions).
- With a host function `sdk.graph.nodes` injected: `sdk.graph.nodes['con'+'structor']('return process')()` returned the real host `process`; `...getBuiltinModule("child_process").execSync("id")` ran and returned the uid line. **codeGeneration does not stop calling the OUTER realm's Function constructor**, because that constructor belongs to the host realm.
- Even when the wrapper is defined inside the context (host fn only in a closure), a **host-realm return value** escapes: `sdk.nodes().constructor.constructor('return process.version')()` -> `v24.14.1` (host array).
- A **thrown host Error** escapes the same way: `try{__t()}catch(e){e.constructor.constructor('return process.version')()}` -> host process.
- A bridge that returns only data **created inside the context** (host passes a JSON string, wrapper does `JSON.parse` using the context's own `JSON`) was NOT escapable in my test (`EvalError`). That is the only safe in-vm shape, and it still relies on the vm boundary, which Node says is not a security boundary (V8 bugs, `Error.prepareStackTrace`/`captureStackTrace`-style leaks, etc.).
- The AST gate fails against this: `obj['con'+'structor']`, `obj[`${'constr'}uctor`]`, destructuring, `Object.getOwnPropertyDescriptor`, etc. are not `.constructor.constructor` syntactically. Blacklisting `globalThis`/`Proxy`/`Reflect` is not complete.
  Sources on the class of bug: vm2 advisories e.g. CVE-2023-37466 (CVSS 9.8, Promise handler sanitization bypass, fixed 3.10.0; GHSA-cchq-frgv-rjh5, https://github.com/advisories/GHSA-cchq-frgv-rjh5, https://osv.dev/CVE-2023-37466). vm2 was discontinued 2023 with maintainer statement that fixing required changing the whole sandbox strategy and recommending isolated-vm (https://github.com/patriksimek/vm2/issues/533); it was revived Oct 2025 (3.10.0) and, per the Jan 2026 thread, the owner says "known escape issues" remain. The exact `Function`-constructor chain is the generic mechanism behind many vm2 advisories (my search results did not quote it; my experiment demonstrates it).
  Corrected wording: "node:vm cannot enforce C_IO = empty. Treat the vm as defense-in-depth only; enforce confinement at a process or OS boundary."

### B6. Worker contents, resourceLimits, timeout -- mostly CONFIRMED

- `process`/`require` inside a Worker: CONFIRMED. Node docs: "Most Node.js APIs are available" in a worker; verified `typeof process`, `require`, `process.getBuiltinModule('fs').readFileSync` all present. So a vm escape inside the worker gets fs/child_process. Workers are not a capability boundary. https://nodejs.org/docs/latest-v24.x/api/worker_threads.html
- `resourceLimits.maxOldGenerationSizeMb`: verified OOM termination: `error ERR_WORKER_OUT_OF_MEMORY "Worker terminated due to reaching memory limit: JS heap out of memory"`, then `exit 1`. Caveats from docs: limits "only affect the JS engine, and no external data, including no `ArrayBuffer`s" and "the process may still abort on a global out-of-memory condition". So Buffers/ArrayBuffers and native allocations bypass it (`new ArrayBuffer(2**31)` style attacks).
- `vm` `timeout` and async code: CONFIRMED with qualification. Verified: a sync infinite loop inside an async function is interrupted (`ERR_SCRIPT_EXECUTION_TIMEOUT`); with `microtaskMode:'afterEvaluate'` a looping `.then` callback is also bounded ("included in the `timeout` scopes"). Without `microtaskMode`, microtasks run after `runInContext` returns, outside the timeout scope; I did not run the unbounded case (it would hang). The RFC does not mention microtaskMode; add it. Timeout does not cover work in host callbacks, and `Atomics.wait`/sync RPC to the host is host time. The outer `worker.terminate()` watchdog is the reliable bound.

### B7. Node permission model -- CONFIRMED stable; per-process; NOT a sandbox

https://nodejs.org/docs/latest-v24.x/api/permissions.html : Stability 2 (Stable); stable since v23.5.0 / v22.13.0 (added v20.0.0 experimental). Flags: `--permission`, `--permission-audit`, `--allow-fs-read`, `--allow-fs-write`, `--allow-child-process`, `--allow-worker`, `--allow-addons`, `--allow-wasi`. It is per-process (can be applied to a spawned child: `node --permission --allow-fs-read=<dir> child.js`). Verified: no-grant child gets `ERR_ACCESS_DENIED` on `child_process.execSync` and on fs reads outside the grant. **Verified: network is NOT restricted** (`net.connect` to 1.1.1.1:80 succeeded under `--permission`). Docs limitations: "Not a security sandbox. Malicious code can bypass it"; symlinks followed; existing fds bypass; docs say workers do not inherit the model (the fetch summary stated this; confirm in current docs before relying); `process._debugProcess(pid)` can signal other Node processes of the same OS user to open the inspector. Corrected RFC text: use `--permission` on a child process as defense-in-depth for fs/child_process, plus separate OS user or container and an egress block for network; do not call it isolation.

### B8. Alternative runtimes

- **isolated-vm**: https://github.com/laverdet/isolated-vm -- README says it is in **maintenance mode** ("will continue to be supported for as long as is technically feasible"; new version in an experimental branch "certainly not ready for serious applications"). Compat table: Node 22 -> isolated-vm 5.x/4.x; **Node 24 -> 6.x or 5.x**; Node 26 -> 7.x; odd Node versions unsupported. Node >=20 needs `--no-node-snapshot`. Needs a compiler toolchain (native addon). Warns it "does not automatically make your application safe", `memoryLimit` is a guideline (attacker can use 2-3x), do not expose `Reference`/`ExternalCopy` to untrusted code, and "run isolated-vm in a separate process from critical infrastructure". RFC claim "frequent compilation failures on Node 24-26" is OVERSTATED: Node 24 is supported (6.x/5.x); the legit points are native build, maintenance mode, and the `--no-node-snapshot` flag. Prebuild availability for Node 24 not independently verified.
- **quickjs-emscripten**: https://github.com/justjake/quickjs-emscripten -- README does not quantify marshalling cost. Says: "makes every effort to be secure, but has not been audited"; pre-1.0; asyncify variants "bigger and run slower"; memory limit (`setMemoryLimit`), time-based interrupt (`shouldInterruptAfterDeadline`) exist; handles must be manually disposed. "15-40 ms marshalling hundreds of objects" is UNVERIFIED and likely overstated if you pass one JSON string across the boundary (a single `JSON.stringify` + `vm.evalCode` of tens of KB is typically sub-ms to low-ms); it is plausible only for per-object handle-by-handle marshalling. Recommend a 1-hour benchmark instead of asserting it. Real costs: ~1 MB WASM, QuickJS interpreter is 10-50x slower than V8 JIT for compute, no JIT.
- **Deno subprocess with permissions**: https://docs.deno.com/runtime/fundamentals/security/ -- default-deny; for untrusted code Deno itself recommends layering: minimal permissions, Web Worker with reduced permissions, OS sandboxing (chroot/cgroups/seccomp), VM/MicroVM. `--allow-run` / `--allow-ffi` ~ `--allow-all`; `eval`/`new Function` run at caller privilege. Better fit than `node:vm` (real network/fs/subprocess denial, including net, which Node permissions lack) but adds a binary dependency.
- **workerd local / Dynamic Workers**: Cloudflare's sandbox is V8 isolate + capability bindings, designed as defense-in-depth with hardware/OS layers, but `@cloudflare/codemode`'s `DynamicWorkerExecutor` needs the Workers runtime. Running `workerd` locally is possible but heavy for a dev-machine MCP; RFC's "8-20 ms IPC" is UNVERIFIED.
- **SES / Hardened JS**: https://github.com/endojs/endo/blob/master/packages/ses/README.md -- `lockdown()` tamper-proofs intrinsics; `Compartment` has its own global, "only the capabilities it is expressly given". Solves the prototype-pollution/constructor-chain class IF you only pass hardened/primitive endowments and do not pass host-realm functions that leak realm (SES `harden`ing of endowments is required). Does NOT bound CPU or memory: guest can "execute for an indefinite amount of time" and "allocate arbitrary amounts of memory". Pair with a Worker + terminate. Reasonable middle option without native deps, but still same-realm, so a V8 bug = escape.
- **ShadowRealm**: TC39 proposal at **Stage 2.7** since Feb 2025 (https://tc39.es/proposal-shadowrealm); I found no later stage change as of the May 2026 changelog. Not shipped in Node/V8 as a stable feature; not usable.

### B9. TS check latency "< 8 ms warm" -- PLAUSIBLE only for tiny scripts; measured

Experiment (`t/ts.js`, TypeScript 5.9.3): one small `.d.ts` (graph nodes/callers), ~10-line script, `lib.es2022`, `skipLibCheck`, reused `oldProgram` + cached SourceFiles: cold first check 102 ms; warm p50 2.6 ms, min 2.2, max 10.2 over 20 runs (syntactic + semantic diagnostics of one file). So <8 ms p95 is plausible for a small SDK d.ts without heavy imports. It will degrade if the d.ts imports `effect` types or the full `lib`, if `skipLibCheck` is off, or if the program is recreated per request. Also GC spikes reach 10 ms. Corrected wording: "~3 ms p50 / ~10 ms worst observed warm with a ~1 KB d.ts; budget 15-25 ms p95 with realistic SDK types; first call ~100 ms."

## C. RFC-0012

### C10. "temp file + rename per file" atomic across files -- WRONG (as stated)

POSIX `rename(2)` is atomic for one path swap only. Sequence of N renames has N commit points; a crash/kill/power loss between renames leaves a mixed old/new tree. The RFC's rollback restores from an **in-memory** snapshot, which is lost on process crash, which is exactly when it is needed (REQ-1.5 only covers "I/O error", not crash). Also missing: `fsync` of temp file before rename and of the directory after; cross-filesystem rename fails (`EXDEV`); editors/watchers see intermediate states; `.harness-tmp-*` leftovers need cleanup.
Sources (general, non-primary lecture/course material from the search): https://courses.cs.washington.edu/courses/cse451/23au/lectures/notes/cc.html , https://www.cs.utexas.edu/~witchel/378AC/lectures/035_crash_consistent_applications-slides.pdf , https://www.usenix.org/system/files/conference/fast17/fast17_pillai.pdf (Pillai et al., FAST'17 on application crash consistency). SQLite's rollback journal / WAL (https://www.sqlite.org/atomiccommit.html) is the canonical multi-file-ish pattern: save originals, write journal, commit marker, delete journal; hot journal => rollback on next open. Git uses lockfile + atomic rename of one ref/index file as the single commit point.
Recommended design (pick one):

1. **Intent journal**: before touching any file, write `.harness/tx/<txId>.json` containing for each path {sha256Before, sha256After, path to saved original under `.harness/tx/<txId>/orig/` and staged new content}, fsync it, then rename files; mark `COMMITTED` (rename journal to `.done`) at the end. On startup (and before every tool call), scan `.harness/tx/`: if journal present and not done, roll back (restore originals, verify hash) or roll forward; make this idempotent via the hashes. Also take a repo-level lock (`mkdir`/`O_EXCL` lockfile like git's index.lock) so two codemods cannot interleave.
2. **Worktree + fast-forward**: apply edits in a throwaway `git worktree`/branch, verify there, commit, then `git merge --ff-only` / `git checkout` into the main tree (git's own index lock gives crash safety; dirty user edits conflict visibly). Heavier, and requires clean paths, but gives free rollback via `git reset`.
3. Minimum: refuse `atomic-commit` if any target path has uncommitted changes (verify `sha256Before`), and call it "best-effort, crash-recoverable via journal", not "atomic".
   Corrected wording: "Commit is atomic per file and crash-recoverable across the batch via an on-disk write-ahead journal and startup recovery."

### C11. ts-morph `useInMemoryFileSystem` -- API CONFIRMED; the isolation design is UNSOUND

https://ts-morph.com/setup/file-system : `new Project({ useInMemoryFileSystem: true })`; also `InMemoryFileSystemHost`; working dir is `/`; standard lib types may resolve as `any` unless `lib`/`target` set (default ES5; note for RFC-0012: set `compilerOptions`, and in-memory FS needs lib files supplied for real type resolution). Note: type-aware transforms in an in-memory project only see what you hydrate; cross-file inference needs the whole dependency closure incl. `node_modules` typings, which RFC says to hydrate lazily (risk: wrong diagnostics).
Passing across boundaries (my tests): a class instance with function members throws `DataCloneError` in `structuredClone`; a plain class instance clones to a plain object with prototype **lost** (`m` undefined). A ts-morph `Project`/`Node` wraps compiler objects with closures and cyclic parent refs; it cannot cross `postMessage`. So the `Project` must be created inside the worker. Then exposing it to a `vm` context in that worker means giving the script host-realm objects, which per B5 yields `project.constructor.constructor('return process')()` = full escape. Also ts-morph exposes `project.getFileSystem()` / `save()` / `getProgram().getTypeChecker()` and `ts` (`ts.sys` has real fs) via `@ts-morph/common` objects, so "ONLY project" is not capability-complete. Mode B is a code-execution capability equal to arbitrary host JS; treat as such: run it in a child process with `--permission` (no fs outside tmp), no network, uid separation, and hard timeouts, or restrict Mode B to a pre-written, harness-reviewed transform library (parameterized), keeping Mode A (declarative ast-grep rules, no code execution) as the only LLM-authored path.

### C12. `@ast-grep/napi` API -- CONFIRMED (with one note)

https://ast-grep.github.io/guide/api-usage/js-api.html : `parse(lang, source)` -> `SgRoot`; `root()` -> `SgNode`; `find(matcher)` / `findAll(matcher)`; `node.replace(text)` -> `Edit`; `node.commitEdits(edits)` -> new source string (called on a node, e.g. `root.commitEdits(edits)`); `Lang` enum exported from `@ast-grep/napi`. The docs page examples use `Lang.JavaScript`; `Lang.TypeScript` exists in the `Lang` enum (language list reference), verify with `import {Lang}` at pin time. Note: `commitEdits` is a node method, not a free function; RFC-0012's prose "findAll + commitEdits" is fine but make sure the code calls `root.commitEdits(edits)`. Also note napi parses with `Lang.Tsx` separately for JSX; `.ts` vs `.tsx` need different Lang values.

### C13. "O(log k) bisection" -- WRONG / OVERSTATED

Zeller & Hildebrandt, "Simplifying and Isolating Failure-Inducing Input", IEEE TSE 28(2), 2002 (https://www.st.cs.uni-saarland.de/papers/tse2002/ ; PDF https://www.st.cs.uni-saarland.de/papers/tse2002/tse2002.pdf ; ISSTA 2000 slides https://faculty.cc.gatech.edu/~harrold/issta00/cfp/slides/zeller.issta2000.pdf). From the ISSTA 2000 slides: number of tests is **|c|^2 + 3|c| in the worst case, log2|c| in the best case** (best case = a single failure-inducing entity). ddmin returns a **1-minimal** set, not a minimum (true minimum would need 2^|c|-1 tests). ddmin also needs the test to be well defined on arbitrary subsets; when changes interfere (a rename in file A and updated callers in B..K; applying only a subset gives a compile error unrelated to the offender), the outcome is "unresolved" and `dd` degrades or fails. The RFC's "invokes binary search over subsets ... <= ceil(log2(k)) checks" assumes monotone, independent edits, which it itself disclaims ("edits across disjoint files are independent") and then applies to the main use case (cross-file refactors).
Corrected wording and practical design: "Fault attribution is best-effort. For independent per-file edits, run per-file shadow checks (O(k) checks, parallelizable) or ddmin (O(k) typical, O(k^2) worst). For interdependent edits, attribute diagnostics to files/rules via the diagnostics' own locations and the rewrite rule that produced each edit (provenance), rather than subset search. If you do bisect, treat 'unresolved' (failing for a different reason) as a first-class outcome and cap checks." Since the shadow check is ~tens of ms and k <= 64, per-diagnostic attribution is cheaper and well-defined.

## Recommended replacement sandbox design for 0011 (minimal)

- Spawn a child process: `node --permission --allow-fs-read=<sandbox-runner-dir> runner.js` (no `--allow-child-process`, no `--allow-worker`, no addons), run as a separate OS user or under a container/bwrap/seccomp with no network; communicate via stdio/IPC with JSON only.
- Inside: bridge returns JSON strings; wrapper parsed by the context's own `JSON`; `vm` with `codeGeneration.strings:false`, `microtaskMode:'afterEvaluate'`, `timeout`; plus SES `lockdown()` optionally. Parent enforces wall-clock kill and RSS cap (`--max-old-space-size`, cgroup).
- Alternatively use Deno with explicit minimal permissions or QuickJS (after benchmarking) if a native boundary is wanted.
- Keep the AST guard as a UX/lint step, not a security control. Reframe the invariant from "C_IO = empty" to "process-level least privilege; read-only snapshot delivered as data".
- Do not call it a theorem in the RFC; remove "mathematically isolated".
